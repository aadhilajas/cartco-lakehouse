# ADR-004: Ingestion Tool Choice

**Status:** Accepted (amended)
**Date:** 2026-07-02
**Amended:** 2026-07-22 — updated to reflect actual implementation (PyArrow + PyIceberg, not PySpark)

## Context

CartCo ingests data from multiple disconnected sources — Shopify e-commerce orders, Amazon marketplace settlement reports, in-store POS events (planned: Kafka), and distributor feeds (planned: SFTP). Each source has different delivery semantics (API pull, file drop, event stream) and different schemas. The ingestion layer must land raw data into Bronze Iceberg tables on MinIO without applying business logic, filtering, or deduplication — those are Silver's responsibility. Each ingestion script must be independently runnable (both from Airflow and directly via `docker exec`) and must produce idempotent writes.

## Decision

Use **per-source Python scripts** in the `ingestion/` directory, each orchestrated as an Airflow task. Each script:
1. Reads its source data (currently synthetic CSVs generated by companion `generate_synthetic_*` scripts).
2. Parses the CSV with **pandas** (`pd.read_csv()`), adds the `ingestion_date` partition column, and converts to a **PyArrow** table via `pa.Table.from_pandas()`.
3. Writes to the Bronze Iceberg table via **PyIceberg 0.7.1** (`table.overwrite(df=arrow_table, overwrite_filter=...)`) through the REST catalog.

The original ADR specified PySpark for ingestion. In practice, the CSV-to-Iceberg path is simple enough that PyArrow + PyIceberg handles it without Spark's overhead. PySpark is installed in `Dockerfile.airflow` and remains available for future use (e.g. if ingestion needs to handle multi-GB files or complex joins), but no current script uses it.

## Consequences

**Positive:**
- Per-source scripts (`shopify_bronze.py`, `amazon_bronze.py`) keep each channel's ingestion logic isolated, testable, and independently deployable.
- Using PyArrow + PyIceberg instead of PySpark avoids Spark session startup overhead (~5–10s), keeping Bronze ingestion fast (~2–3s for 50k rows).
- pandas is acceptable in `ingestion/` for CSV parsing because Bronze is a format-conversion layer, not a transform layer. The "no pandas in transforms" rule applies only to `transforms/`.
- Each script emits OpenLineage START/COMPLETE/FAIL events via `lineage/emitter.py`, giving Marquez visibility into Bronze writes.
- Scripts are callable both as Airflow tasks (`BashOperator` in the DAG) and directly (`docker exec ... python ingestion/shopify_bronze.py`), which simplifies debugging.

**Negative:**
- No Spark means no distributed processing — a single-threaded PyArrow pipeline cannot scale horizontally. Acceptable for the current data volumes (40k–50k rows per source).
- pandas is used for CSV parsing in the ingestion path, creating a dependency that the transform path deliberately avoids. This asymmetry is documented but could confuse future contributors.
- Each source gets its own script with repeated boilerplate (catalog setup, `ensure_table()`, `read_source_csv()`, logging). A shared base class or utility module could reduce duplication but was deferred to keep each script self-contained and readable.

## Alternatives Considered

- **PySpark batch scripts (original plan):** Would provide distributed processing and a single engine for both ingestion and transforms. Rejected for the current implementation because the data volumes don't justify Spark's startup overhead, and PyIceberg's `table.overwrite()` API is simpler for the CSV-to-Iceberg use case. PySpark remains installed for future migration if data volumes grow.
- **Fivetran / Airbyte:** Managed connectors that handle extraction and loading automatically. Out of scope for the local-first internship deliverable — these require cloud accounts or complex self-hosted setups, and the learning objective is to build the pipeline from scratch.
- **Apache Spark Structured Streaming (for Kafka POS):** Still the planned approach for the in-store Kafka source, which has streaming delivery semantics. Not yet implemented.
